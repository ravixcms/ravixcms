# معماری چندسایتی

**وضعیت صادقانه: پایه (foundation) پیاده‌سازی شده، نه چندسایتی کامل.**

## مدل‌ها (`apps/sites`)
- `Site` (نام، مالک، `is_default`، فعال/غیرفعال) · `SiteDomain` (دامنهٔ یکتا) · `SiteMember` (نقش owner/manager/staff).
- مهاجرت دادهٔ `0002` سایت پیش‌فرض «main» را می‌سازد.

## حالت‌ها (`RAVIN_MULTISITE_ENABLED`)
- **false (پیش‌فرض):** فقط سایت پیش‌فرض؛ دسترسی همان نقش‌های قبلی.
- **true:** سایت از هدر `Host` تشخیص داده می‌شود؛ دامنهٔ ناشناخته/غیرفعال ⇒ ۴۰۴ برای فروشگاه؛ ورود به پنل هر سایت نیازمند عضویت (مدیرکل مستثنی).

## جداسازی داده
- **فروشگاه کاملاً سایت‌محور است:** `Product` و `Order` کلید `site` دارند؛ همهٔ کوئری‌های عمومی/پنل/API فیلتر می‌شوند؛ دسترسی با pk سایت دیگر ⇒ ۴۰۴ (تست شده).
- سایت فعال پنل در نشست (`ravin_active_site`) ذخیره و **در هر درخواست دوباره با دسترسی واقعی اعتبارسنجی می‌شود** (دست‌کاری نشست اثری ندارد).
- مدیریت سایت‌ها/دامنه‌ها/اعضا فقط برای مدیرکل (`sites.manage`).

## باقی‌مانده (نیازمند تغییر بنیادین)
نوشته‌ها، برگه‌ها، رسانه، قالب/تنظیمات سایت و افزونه‌ها **هنوز سایت‌محور نیستند** و بین سایت‌ها مشترک‌اند. مسیر پیشنهادی:
1. افزودن `site` (nullable) به این مدل‌ها + مهاجرت داده به سایت پیش‌فرض، سپس NOT NULL.
2. یک `SiteScopedManager`/mixin مشترک برای فیلتر خودکار، یکتایی slug به‌ازای سایت.
3. تفکیک مسیر `media/` به‌ازای سایت و تنظیمات قالب به‌ازای سایت.
4. تست‌های نشت داده برای هر مدل (الگو: `apps/sites/tests/test_sites.py`).
تا آن زمان، برای چند مشتری مستقل واقعی، **چند استقرار جداگانه** امن‌تر است.
