# سیستم افزونه‌ها (مرحله پنجم)

ترجمهٔ افزونه (پوشهٔ `locale/` با gettext استاندارد): [`translation.md`](translation.md).

افزونه‌ها قابلیت‌های جدید (فرم‌ساز، فروشگاه، چت آنلاین، ...) را **بدون ویرایش هسته** اضافه می‌کنند. هر افزونه یک پوشه در `plugins/` است
با یک قرارداد اعلامی (`plugin.json`) و کد پایتون.

> **مهم‌ترین نکتهٔ امنیتی:** افزونه کد پایتون است و با همان دسترسی سرور اجرا می‌شود؛ پایتون را نمی‌شود سندباکس کرد.
> بنابراین امنیت این سیستم بر **اعتماد صریح مدیر + قفل‌کردن کدِ تأییدشده** بنا شده است، نه بر محدودکردن کد.
> فقط افزونه‌هایی را نصب کنید که کدشان را دیده‌اید یا از منبع مورد اعتماد آمده‌اند.

## چرخهٔ عمر و مدل امنیتی

```
پوشه در plugins/ ──(شناسایی: فقط plugin.json خوانده می‌شود، کدی اجرا نمی‌شود)──► «آمادهٔ نصب»
      │  مدیر در پنل: مشخصات + فهرست فایل‌ها + اثرانگشت SHA-256 را می‌بیند، تیک «اعتماد دارم» را می‌زند
      ▼
   نصب  ──► اثرانگشت تأییدشده ذخیره می‌شود؛ (اگر مدل دارد) مهاجرت‌ها اعتبارسنجی و اجرا می‌شوند ──► «نصب‌شده، غیرفعال»
      │  مدیر: فعال‌سازی (کنترل سازگاری و وابستگی‌ها دوباره)
      ▼
   فعال ──► در هر درخواست: اثرانگشت پوشه == اثرانگشت تأییدشده؟ بله ← اجرا. خیر ← توقف فوری + رویداد tamper
```

| تضمین | چگونه |
|---|---|
| کد ناشناس اجرا نمی‌شود | شناسایی فقط `plugin.json` را می‌خواند؛ import فقط برای افزونهٔ **نصب‌شده + فعال + با اثرانگشت تأییدشده** |
| بارگذاری/فعال‌سازی خودکار نداریم | نصب و فعال‌سازی دو عمل جدا و فقط با POST + CSRF + مجوز `plugins.manage` (مدیر/مدیرکل) |
| تغییر کد بعد از تأیید | هر فایل (حتی افزودن فایل یا symlink) اثرانگشت را عوض می‌کند ← افزونه تا تأیید دوباره متوقف می‌شود |
| bytecode دست‌کاری‌شده | یابندهٔ import اختصاصی فقط منبع تأییدشده را کامپایل می‌کند و `__pycache__` را نمی‌خواند |
| دور زدن مجوزها | مجوز هر صفحهٔ مدیریتی را **هسته** پیش از فراخوانی افزونه بررسی می‌کند؛ مجوز افزونه فقط به مدیر/مدیرکل داده می‌شود و نمی‌تواند مجوز هسته را بازتعریف کند |
| CSRF | مسیرهای افزونه فقط از طریق توزیع‌کنندهٔ هسته در دسترس‌اند؛ افزونه نمی‌تواند `csrf_exempt` کند |
| خروجی hook سئو | هسته آن را پاک‌سازی می‌کند (کلیدها، نشانی‌ها، robots)؛ افزونه نمی‌تواند JSON-LD یا HTML به `<head>` تزریق کند |
| خطای افزونه پنل را نمی‌خواباند | همهٔ فراخوانی‌ها در try/except؛ صفحهٔ خطای دوستانه + ثبت در گزارش؛ قطع‌کنندهٔ مدار |
| مهاجرت دیتابیس | بررسی ایستا: فقط عملیات ساختاری مجاز (نه `RunPython`/`RunSQL`)، جدول‌ها `plugin_<slug>_*`، ارتباط فقط با خود افزونه و کاربر |

اثرانگشت یک بازبینی هنگام **بارگذاری** و سپس هر ۵ ثانیه برای افزونهٔ بارگذاری‌شده است؛ یعنی دستکاری تا حداکثر ~۵ ثانیه
(و برای هر `import` جدید همان لحظه) شناسایی می‌شود.

## ساخت اولین افزونه

```bash
python manage.py startplugin my_hello --name "سلام" --author "من"      # اسکلت در plugins/my_hello (با --models برای مدل دیتابیس)
python manage.py check_plugins my_hello                                  # بررسی manifest و سازگاری (کدی اجرا نمی‌شود)
```

سپس در پنل: **افزونه‌ها ← سلام ← بررسی و نصب ← فعال‌سازی**. اسکلت یک صفحهٔ مدیریتی، یک تنظیم و یک مجوز دارد:

```
plugins/my_hello/
├── plugin.json        قرارداد (اعلامی)
├── __init__.py        خالی/بدون عوارض جانبی
├── views.py           def hello(request, api): ...
├── templates/hello.html     {% extends "plugins/page.html" %}
├── models.py + migrations/  (اختیاری)
```

## قرارداد plugin.json

```json
{
  "slug": "contact_form",                 // = نام پوشه؛ [a-z][a-z0-9_]{2,30}
  "name": {"fa": "فرم تماس", "en": "Contact form"}, "version": "1.0.0", // نام و description رشتهٔ ساده یا {کد زبان: متن}؛ نسخه سه‌بخشی
  "description": "...", "author": "...", "homepage": "https://...",
  "api_version": 1,                       // نسخهٔ قرارداد افزونه‌ها (باید با هسته برابر باشد)
  "ravix": ">=0.5.0,<1.0.0",              // بازهٔ سازگاری با Ravix (الزامی)
  "requires": {"other_plugin": ">=1.0.0"},// وابستگی به افزونه‌های دیگر (باید نصب و فعال باشند)
  "models": true,                         // مدل/جدول دارد؟
  "capabilities": {"contact_form.view": "مشاهدهٔ پیام‌ها"},
  "settings": [ {"key": "...", "label": "...", "type": "text|textarea|bool|int|choice|email|url", "default": ...} ],
  "admin_pages": [ {"key": "inbox", "title": "پیام‌ها", "view": "views:inbox", "capability": "contact_form.view",
                    "menu": true, "icon": "mail", "section": "content", "order": 70} ],
  "public_routes": [ {"path": "", "view": "views:form", "methods": ["GET", "POST"]} ],
  "hooks": [ {"name": "public.seo", "handler": "hooks:apply_seo", "priority": 50} ]
}
```

- کلید ناشناخته = خطا (جلوگیری از غلط‌املایی و ادعاهای پنهان).
- `view`/`handler` همیشه `"ماژول:تابع"` است و ماژول **نسبت به بستهٔ همان افزونه** import می‌شود (نمی‌تواند به `os` یا ماژول‌های هسته اشاره کند).
- مجوزها باید با `"<slug>."` شروع شوند. اگر `capability` صفحه ذکر نشود، پیش‌فرض امن‌ترین حالت (`plugins.manage`) است.
- آیکن‌های مجاز از مجموعهٔ آیکن‌های پنل‌اند؛ بخش‌های منو: `main | content | appearance | system`.

## PluginAPI

هر ویو و hook نمونه‌ای از `PluginAPI` می‌گیرد؛ تنها راه رسمی تعامل با هسته (قرارداد نسخهٔ ۱):

| عضو | کار |
|---|---|
| `api.slug / name / version` | مشخصات افزونه |
| `api.setting(key, default)` / `api.settings()` | تنظیمات **اعتبارسنجی‌شدهٔ** همین افزونه |
| `api.log(message, level="info"\|"warning"\|"error")` | رویداد در «گزارش افزونه‌ها» |
| `api.audit(request, message)` | ثبت در گزارش رویدادهای مدیریتی |
| `api.has_cap(user, "x.y")`، `api.cap("view")` | بررسی مجوز با سیستم هسته |
| `api.admin_url(page_key)`, `api.redirect_admin(key)`, `api.public_url(path)` | ساخت نشانی |
| `api.render_admin(request, "t.html", ctx, title=...)` | رندر قالب افزونه در چارچوب پنل |
| `api.render_public(request, "t.html", ctx, title=...)` | رندر قالب افزونه داخل قالب فعال سایت (هدر/فوتر/منو) |
| `api.rate_limit(request, bucket, limit, window)` | True اگر درخواست مجاز است (بر پایهٔ IP) |
| `api.site` | تنظیمات سایت |

قالب‌های افزونه با نام `plugin:<slug>/<مسیر>` از پوشهٔ `templates/` همان افزونه بارگذاری می‌شوند؛ نمی‌توانند قالب‌های هسته را بپوشانند و
خروج از پوشه (`..`) ممکن نیست. قالب‌های مدیریتی باید `{% extends "plugins/page.html" %}` و بلوک `plugin_content` را پر کنند.

## صفحات مدیریتی، منو و مجوزها

هر `admin_pages[*]` در نشانی `/panel/plugins/x/<slug>/<key>/` ثبت می‌شود و (اگر `menu` درست باشد) خودکار در منوی کناری می‌آید (فقط برای کسانی که
مجوزش را دارند). ویو `def view(request, api)` است و باید `HttpResponse` برگرداند.

**نیازی به بررسی مجوز در ویو نیست** (هسته پیش از فراخوانی انجام داده)، ولی برای عملیات حساس‌تر می‌توانید `api.has_cap(...)` را هم بزنید.
مجوزهای اعلام‌شدهٔ افزونه فقط به `admin` و `super_admin` تعلق می‌گیرد.

```python
def inbox(request, api):
    if request.method == "POST":           # CSRF را هسته اعمال می‌کند؛ در قالب {% csrf_token %} بگذارید
        ...
        return api.redirect_admin("inbox")
    return api.render_admin(request, "inbox.html", {"items": ...}, title="پیام‌ها")
```

## مسیرهای عمومی

`public_routes[*]` در `/ext/<slug>/<path>` سرو می‌شود. فقط `GET` و `POST` مجاز است؛ روش‌های دیگر ۴۰۵ می‌گیرند. صفحهٔ عمومی را با
`api.render_public(...)` در قالب سایت بسازید. نکات:

- پاسخ‌هایی که توکن CSRF دارند باید `Cache-Control: private, no-store` باشند (به‌طور پیش‌فرض اگر چیزی نگذارید همین گذاشته می‌شود).
- ورودی کاربر را **همیشه** با `forms.Form` اعتبارسنجی کنید؛ برای فرم‌های عمومی `api.rate_limit` و یک تلهٔ honeypot بگذارید (نمونه: `contact_form`).
- `/ext/` برای نامک صفحات ثابت رزرو است.

## تنظیمات افزونه

با `settings` در manifest اعلام می‌شود. هسته فرم صفحهٔ تنظیمات را می‌سازد و **اعتبارسنجی** می‌کند (طول، بازه، فهرست انتخاب، ایمیل، نشانی امن).
مقدار تنظیم فقط در دیتابیس (رکورد افزونه) است؛ با `api.setting("key")` بخوانید. انواع: `text, textarea, bool, int, choice, email, url`.
نکته: رمز/توکن حساس در تنظیمات نگذارید (در دیتابیس به‌صورت متن ساده است)؛ برای آن‌ها از متغیر محیطی استفاده کنید.

## مدل‌ها و مهاجرت دیتابیس

با `"models": true`، بستهٔ افزونه یک اپ جنگو با برچسب `plugin_<slug>` می‌شود. قواعد (در نصب اعمال می‌شود):

- جدول‌ها باید با `plugin_<slug>_` شروع شوند (پیش‌فرض همین است؛ `db_table` دستکاری‌شده رد می‌شود).
- ارتباط (`ForeignKey`...) فقط به مدل‌های خود افزونه یا `settings.AUTH_USER_MODEL`؛ برای صفحه/نوشته فقط شناسهٔ عددی نگه دارید (نمونه: `seo_toolkit`).
- مهاجرت‌ها فقط عملیات ساختاری دارند (`CreateModel/AddField/AlterField/...`). **`RunPython` و `RunSQL` ممنوع‌اند** و وابستگی مهاجرت به اپ‌های هسته مجاز نیست.

```bash
python manage.py plugin_makemigrations my_plugin    # فقط DEBUG: ساخت مهاجرت (کد بدون تأیید بارگذاری می‌شود)
```

پس از ساخت مهاجرت، کد تغییر کرده و باید دوباره بررسی/تأیید شود. نصب مهاجرت‌ها را اجرا می‌کند؛ حذف با «پاک‌کردن داده‌ها» مهاجرت‌ها را به صفر برمی‌گرداند.
اگر نصب با خطای مهاجرت شکست بخورد، رکورد نصب برگردانده می‌شود.

## Hookها

فقط hookهای فهرست رسمی (`apps/plugins/hooks_registry.py`) قابل ثبت‌اند:

| نام | نوع | امضا | کاربرد |
|---|---|---|---|
| `public.seo` | filter | `fn(seo, api, *, kind, obj_id, site, request)` ← dict | تغییر سئوی صفحه (`kind` = `page`/`post`) |
| `content.saved` | action | `fn(api, **ctx)` | (رزرو برای نسخه‌های بعد) |
| `comments.before_save` | filter | `fn(data, api, *, post_id, request)` ← dict | بررسی دیدگاه پیش از ذخیره (مثلاً ضداسپم خارجی). `data` شامل `author_name, author_email, body, status, ip, parent_id` است |
| `comments.created` | action | `fn(api, *, comment_id, post_id, status, request)` | پس از ثبت دیدگاه عمومی |
| `shop.order_status_changed` | action | `fn(api, *, order_id, number, old_status, new_status, phone, language, text)` | پس از تغییر وضعیت سفارش فروشگاه (hook پیامک) |
| `comments.status_changed` | action | `fn(api, *, comment_id, old, new, request)` | پس از تغییر وضعیت توسط مدیر (تأیید، اسپم، زباله، …) |

خروجی `comments.before_save` فقط کلید `status` را می‌تواند تغییر دهد و فقط به `pending` یا `spam`؛ افزونه نمی‌تواند دیدگاه را خودکار تأیید کند یا متن را عوض کند.

خروجی `public.seo` تنها این کلیدها را می‌تواند تغییر دهد: `title, description, canonical, robots, og_type, og_image`؛ بقیه نادیده گرفته می‌شود.
خطای hook ثبت می‌شود و مقدار قبلی حفظ می‌شود (صفحهٔ سایت نمی‌افتد). hookهای جدید با افزودن یک سطر در `hooks_registry.py` و یک `apply_filter/run_action` در هسته اضافه می‌شوند.

## خطا، گزارش و غیرفعال‌سازی خودکار

- هر خطای ویو/hook/بارگذاری در **پنل ← افزونه‌ها ← گزارش افزونه‌ها** با traceback (فقط برای مدیر) ثبت می‌شود. کاربر عادی متن خطا را نمی‌بیند.
- **قطع‌کنندهٔ مدار:** اگر یک افزونه در `RAVIX_PLUGIN_ERROR_WINDOW` ثانیه (پیش‌فرض ۶۰۰) به `RAVIX_PLUGIN_ERROR_LIMIT` خطا (پیش‌فرض ۵) برسد، خودکار غیرفعال می‌شود
  (وضعیت «غیرفعال‌شده خودکار»؛ مدیر پس از رفع مشکل می‌تواند دوباره فعال کند).
- شکست بارگذاری، گم‌شدن پوشه یا دستکاری کد هم افزونه را فوراً غیرفعال و رویداد ثبت می‌کنند.
- رویدادهای مدیریتی (نصب، فعال‌سازی، تنظیمات، حذف) هم در گزارش افزونه‌ها و هم در گزارش رویدادهای مدیریتی ثبت می‌شوند.
- نگهداری: `python manage.py plugin_purge_events --days 90`.

## به‌روزرسانی افزونه

فایل‌ها را جایگزین کنید (نسخهٔ جدید در `plugin.json`). افزونه بلافاصله متوقف و در پنل «تغییر کد؛ نیازمند تأیید» می‌شود. مدیر تغییرات را می‌بیند
و تأیید می‌کند (مهاجرت‌های جدید اجرا می‌شود)؛ سپس باید **دوباره فعال** کند. افزونه‌های دارای مدل پس از تأیید به راه‌اندازی مجدد سرور
(ورکرها) نیاز دارند؛ تا آن‌زمان در آن پردازه بارگذاری نمی‌شوند (رویداد `restart_required`).

## پیکربندی سرور و حالت امن

| متغیر | پیش‌فرض | معنی |
|---|---|---|
| `RAVIX_PLUGINS_ENABLED` | `true` | `false`: سیستم افزونه کاملاً خاموش (کلید اضطراری) |
| `RAVIX_PLUGINS_SAFE_MODE` | `false` | `true`: هیچ کد افزونه‌ای اجرا نمی‌شود، ولی مدیریت (حذف/گزارش) باز است. برای بازیابی |
| `RAVIX_EXTRA_PLUGIN_DIRS` | — | پوشه‌های اضافهٔ افزونه (با کاما)؛ فقط مسیرهای مورد اعتماد |
| `RAVIX_PLUGIN_ERROR_LIMIT` / `_WINDOW` | `5` / `600` | قطع‌کنندهٔ مدار |

پوشهٔ `plugins/` را برای کاربر وب‌سرور **فقط‌خواندنی** کنید؛ هر که بتواند فایل بنویسد ولی تأیید مدیر ندارد، نمی‌تواند کدش را اجرا کند (اثرانگشت)،
اما ایدهآل این است که اصلاً نتواند بنویسد. پنل مدیریت افزونه‌ها فایل آپلود نمی‌کند (عمداً)؛ کد با دسترسی سرور/استقرار می‌آید.

```bash
python scripts/e2e_plugins.py               # سناریوی کامل در مرورگر واقعی
```

برای آزمون افزونهٔ خودتان از الگوی `apps/plugins/tests/helpers.py` (`PluginTestCase`، پوشهٔ موقت و `write_plugin`) استفاده کنید.
آزمون‌هایی که مهاجرت اجرا می‌کنند باید `TransactionTestCase` باشند (محدودیت SQLite).

## افزونه‌های نمونه

- **`contact_form`** — فرم تماس در `/ext/contact_form/`؛ پیام‌ها در جدول `plugin_contact_form_contactmessage`؛ صندوق پیام در پنل (خوانده/حذف)؛
  تنظیمات: پیام موفقیت، ایمیل اطلاع‌رسانی، سقف ارسال در ساعت، متن بالای فرم. حفاظت: CSRF، اعتبارسنجی، honeypot، rate limit، escape خروجی.
- **`seo_toolkit`** — عنوان، توضیحات متا، noindex، canonical و تصویر اشتراک‌گذاری هر صفحه/نوشته؛ الگوی عنوان سراسری، robots و توضیحات پیش‌فرض.
  از hook `public.seo` استفاده می‌کند و بدون FK به مدل‌های هسته کار می‌کند.

## مسیر توسعه

ساختار برای افزونه‌های بزرگ‌تر آماده است: **فروشگاه** (مدل محصول/سفارش + صفحات مدیریتی + مسیرهای عمومی سبد + مجوزهای `shop.*`)،
**فرم‌ساز** (مدل فرم/پاسخ + `requires` به `contact_form` یا مستقل)، **چت آنلاین** (مسیرهای عمومی POST/GET با rate limit؛ برای WebSocket/Realtime باید زیرساخت جداگانه
افزوده شود). نقاط توسعهٔ هسته: `hooks_registry.py` (hookهای جدید)، `PluginAPI` (قابلیت‌های جدید با افزایش `PLUGIN_API_VERSION` در صورت ناسازگاری)،
و `NavItem.url` برای منوی پویا.

## محدودیت‌ها

- سندباکس پایتون وجود ندارد؛ اعتماد به کد با مدیر است (توضیح بالا).
- بازبینی اثرانگشت هر ≈۵ ثانیه است؛ در این فاصله کدِ قبلاً بارگذاری‌شده ادامه می‌دهد.
- افزونهٔ دارای مدل پس از به‌روزرسانی به راه‌اندازی مجدد نیاز دارد؛ مدل‌های ثبت‌شده از حافظه برداشته نمی‌شوند.
- ابزار نصب از طریق آپلود فایل ZIP عمداً وجود ندارد (سطح حملهٔ بزرگ).
